# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A manga/image viewer for local image folders, reachable only from inside a Tailscale tailnet, gated by Google OAuth. FastAPI backend + a single self-contained HTML template. Docs and some commit messages are in Japanese.

## Commands

Run the test suite (Playwright UI tests against a live server):

```bash
uv run --with pytest --with playwright --with-requirements requirements-dev.txt pytest tests/ -q
```

Run a single test:

```bash
uv run --with pytest --with playwright --with-requirements requirements-dev.txt pytest tests/test_ui.py::test_search_filters_current_level -q
```

First time only, if Chromium is missing:

```bash
uv run --with playwright playwright install chromium
```

`--with-requirements requirements-dev.txt` is required even though `tests/README.md` and the `conftest.py` docstring omit it — the `server` fixture spawns `sys.executable -m uvicorn`, and `uvicorn[standard]` lives in `requirements-dev.txt`, not in the runtime `requirements.txt` (which ships only hypercorn), so fastapi/uvicorn must be in the same environment as pytest.

Run the app locally without Docker or OAuth:

```bash
BOOKQ_TEST_MODE=true DOWNLOADS_DIR=/path/to/images uv run --with-requirements requirements-dev.txt uvicorn app.main:app --port 8080
```

Bring up a throwaway development environment for the current worktree (Docker, no OAuth, reachable from the tailnet — each environment takes one of ten fixed slots (node `dev-XX`, XX = 01..10), so no port allocation or shared gateway):

```bash
./dev.sh up
```

**After finishing an implementation, verify it in this environment before calling the work done**: `./dev.sh up`, check the change there, then `./dev.sh down` once you're done — don't leave it running.
Full deployment (requires `.env` and a `TS_AUTHKEY` in the shell or in `.env`) — **main checkout only**:

```bash
./prd.sh
```

There is no linter or formatter configured.

## Architecture

### Two containers, one reachable path

`docker-compose.yml` runs `viewer` (FastAPI on :8080) and a `tailscale` sidecar. **The viewer publishes no host port** — the only route in is `tailscale serve` terminating HTTPS on :443 and proxying to `viewer:8080` inside the compose network. Consequences worth knowing:

- Nothing on the host can reach the viewer directly, so liveness has to be checked from *inside* the container. That is what the `healthcheck` in `docker-compose.yml` is for; `rebuild.sh` (the shared deploy engine behind `prd.sh up` and `dev.sh up`) waits on it and then curls the public URL, which is the only check that catches "container is up but the proxy isn't serving it".
- **If `viewer` is not on the `bookq_default` network, the site returns 502** — `tailscale serve` resolves the literal name `viewer` through compose DNS. This has happened for real: a hand-started container inherited the compose labels `project=bookq, service=viewer` while sitting on the default `bridge` network. Diagnose with `docker inspect $(docker compose ps -q viewer) --format '{{json .NetworkSettings.Networks}}'`.
- The host mount path defaults to `./downloads`; override with `DOWNLOADS_HOST_DIR`.
- Production runs single-worker `hypercorn` behind `tailscale serve` (TLS/HTTP-2 terminates at the sidecar proxying plain HTTP to `viewer:8080`; hypercorn's own HTTP/2 never reaches clients). `WEB_CONCURRENCY` is intentionally unset — hypercorn ignores it. Tests run `uvicorn`. `hypercorn` is in the runtime `requirements.txt`; `uvicorn[standard]` is dev-only, in `requirements-dev.txt`.

### Production vs. development environments

One production stack, any number of development stacks, designed so several agents can drive it concurrently. See [docs/deployment.md](docs/deployment.md) for the full workflow.

- Production is `docker-compose.yml`, project `bookq`, viewer + tailscale sidecar, HTTPS on `bookq.…ts.net`, real OAuth.
- A development environment is `docker-compose.dev.yml`, project `bookq-dev-pool-XX`, one of ten fixed slots. `./dev.sh up <name>` takes the first free slot and maps `<name>` to it via the `com.bookq.name` / `com.bookq.pool_slot` labels; re-running `up <name>` reuses the same slot.
- A dev environment's URL is its slot: `https://dev-XX.…ts.net` (XX = 01..10). `./dev.sh url <name>` resolves it. `down` keeps the tailscale state volume so the slot's node identity survives; only `down --full` resets it.
- **`dev.sh` builds the image itself** for `--ref <branch|tag|SHA>` straight from `git archive <sha>`, so the result depends only on the commit, not on any working tree, and needs no worktree. Omitting `--ref` builds from the current working tree instead. Unused/dangling dev images are reclaimed by `./dev.sh gc` (also auto-run after every successful `up`).
- Three properties make it safe under parallel agents, and they are the ones to preserve:
  1. **Environments share nothing.** Separate compose projects, networks, volumes, and tailnet nodes. No shared mutable resource exists, so there is no lock.
  2. **URLs are deterministic per slot, not per name.**
  3. **No state file.** Name, ref, commit, branch, worktree all live in `com.bookq.*` labels, readable even on stopped containers — that is what keeps `up` idempotent and URLs stable.
- **Never run a bare `docker compose up` in a worktree.** Compose derives the project name from the directory, so you get a second stack *including a tailscale sidecar* that fights production for the hostname `bookq`. `prd.sh` refuses to run from a linked worktree; `dev.sh` passes `-p` explicitly, and even a deliberate `docker compose -f docker-compose.dev.yml up` fails before it can start anything because the `DEV_IMAGE`/`DEV_NAME` (`:?`) variables are unset in a worktree. `rebuild.sh` deliberately has no guard because it is the shared deploy engine for both prd and dev.
- The git hooks (`.githooks/`, installed by `./setup-hooks.sh`) rebuild *the worktree's own development environment* on commit, never production. Markers are per-worktree, and hooks no-op when their worktree files are absent.

### Auth and the test-mode bypass

`app/auth.py` does Google OAuth via authlib, storing the user dict in starlette's `SessionMiddleware` signed cookie (registered in `app/main.py`). Access control is an email allowlist: `ALLOWED_EMAILS` → `Settings.allowed_emails_set`, checked in the callback. `BASE_URL` must be set explicitly because the redirect URI can't be derived correctly from behind the Tailscale proxy.

`BOOKQ_TEST_MODE=true` makes `get_current_user` / `require_auth` return a mock user and skip all OAuth. It is read **once at import time** into a module-level `_TEST_MODE`, so it must be in the environment before the process starts. The whole test suite depends on this.

### The folder tree is the tricky part

`app/scanner.py:scan_tree` recursively builds nodes of `{name, type: "folder"|"image", children}`. Two rules produce most of the surprising behavior:

- **Single-child flattening**: a folder with no images and exactly one subdirectory is collapsed — the child's nodes are hoisted into the parent with `name` rewritten to `"parent/child"`, and `thumb`/`thumbs` paths rewritten to match. A deep one-way chain becomes one UI row. Any change here must keep the three path rewrites in sync (see commit `a5cc5e3`, which fixed a lookup that used the wrong side of this).
- **Thumbnails**: folder nodes get `thumb` (first image found depth-first in the subtree) and, only when 2+ immediate subfolders have thumbs, `thumbs` (up to 9). The UI switches to a multi-thumb grid based on `thumbs.length`.

Filenames sort naturally by embedded digits (`1 < 2 < 10`); directories too, so episode folders order `ch-2 < ch-10` (tie-break by raw name). Kanji numerals (漢数字) in numeric slots are normalized too (第X部/第X話): `【第一部】 < 【第二部】 < 【第十話】` — context-guarded, so proper nouns like 千尋/六本木 are never converted. `/api/folders` rescans the tree on every request; the metadata index it merges in is cached for 300 s per worker process (`_ensure_index`).

**Archives are virtual folders.** `app/archive.py` owns `ARCHIVE_EXTENSIONS` (`.zip .cbz .rar .cbr .epub`): `scan_tree` turns each archive file into a `folder` node whose children are its image entries, `/api/images` lists them, and `/image/<archive>/<inner>` serves one entry on demand via `read_archive_entry` (never a 500 — bad archives list as `[]`, bad entries 404). ZIP/RAR entries sort naturally; EPUB follows the OPF spine (`<img>` / SVG `<image>` per page, `%20` decoded) and falls back to natural order when the package is unreadable. RAR listing needs no extractor at all — `rarfile` parses RAR headers in pure Python, and store-method entries even read without a tool; only reading a *compressed* entry requires one, and without it that read answers 501. Docker installs Debian `7zip`; on macOS use `brew install sevenzip` — rarfile 4.5's built-in `bsdtar` backend mis-parses its own argv and returns corrupt data, so it is not a usable extractor. PDF stays in `app/archive_pdf.py`. Test fixtures write RAR5 by hand (`tests/fixtures/rar5.py`), so no `rar` binary is needed to run the suite. RAR pages are served by re-parsing the archive and, for compressed entries, spawning one extractor process per page; solid RAR archives are therefore slow to page through (extracting entry n decompresses 0..n) and are not cached, matching the PDF path.

Known gap, covered by a characterization test: a folder holding *both* images and subfolders drills down to the subfolders only, so its direct images are unreachable from the UI.

### Path containment

`/api/images` and `/image/{path}` go through `_is_within()` in `app/routes.py`, which resolves both paths and uses `Path.is_relative_to`. Symlink loops and other unresolvable targets resolve to "outside" (403), not 500. `tests/test_traversal.py` covers the bypass attempts; add a case there before touching this function.

### Frontend: one template, plain scripts

`app/templates/index.html` (~230 lines) holds the markup plus a few inline snippets: the `__BOOKQ_TEST_MODE__` flag near the top, the `?thumb_perf` probe panel, and a stale-shell watchdog at the bottom. The watchdog must live in the document itself (navigations are NetworkFirst so the html is always fresh, while `/static/*` is StaleWhileRevalidate and can lag a deploy behind — a watchdog inside a swappable asset could never detect its own staleness). It asserts the globals this deploy's scripts export; on a miss it deletes only the `.js` entries inside the `bookq-shell-*` caches (never `/`, `offline.html`, or images — offline boot must survive), nudges `registration.update()`, and reloads at most once per mismatch streak per tab session (the sessionStorage flag is cleared on the next healthy load). It skips repair entirely in test mode and when `navigator.onLine` is false. All other behaviour lives in `app/static/app.js` plus ~20 global-script modules loaded before it in `defer` order (`offline-core`, `thumbs/resolveCover`, `browse/hash`, `browse/render`, `browse/scroll`, `search/facets`, `offline/storeAdapter`, `thumbs/prefetch`, `viewer/spread`, `viewer/navigation`, `viewer/gesture`, `viewer/zoom`, `viewer/overview`, `viewer/pairUI`, `viewer/pairModel`, `viewer/pairedView`, `viewer/pairTransport`, `viewer/pairClient`, `viewer/pairController`, `browse/pairSync`; plus vendor `qrcode.min.js`/`jsQR.min.js`, and `login.js` on the unauthenticated branch). No build step, no external assets. Load order is a contract: `sw.js` SHELL_ASSETS must list the same files.

`app/routes.py` keeps one module-level `jinja2.Environment(auto_reload=True, cache_size=0)`, so template edits apply without a restart.

Service Worker / PWA: `app/static/sw.js` is served at `/sw.js` (and `/static/sw.js`) via `app/routes.py` FileResponse with `Service-Worker-Allowed: /` so scope `/` is allowed. Registration lives in `app/static/app.js` init block (`navigator.serviceWorker.register('/sw.js', {scope:'/'})`, updatefound toast). **The controllerchange listener reloads only when the page already had a controller** — a first install activates via `skipWaiting` + `clients.claim`, which fires the same event, and reloading there discards the book being read (it also destroys Playwright's execution context mid-test). Offline strategy: images CacheFirst per-work (`bookq-work-<encodeURIComponent(folder)>-v1`, fallback `bookq-images-fallback`), API NetworkFirst (`bookq-api-v1`), navigate NetworkFirst falling back to the same-URL cache, then `/static/offline.html`, then the precached `/` — **offline.html must stay ahead of `/`**, which is precached unconditionally and would otherwise answer every offline navigation. Range bypass, navigationPreload enabled.

**`app/static/offline-core.js` is the single source for the IndexedDB store, `cacheNameFor`, byte formatting, the dedup sum, and `encodePath`/`imageUrl`.** It is a plain global script loaded before `app.js` and before the harness's inline script; both consume `window.OfflineCore`. Viewer conventions that will bite if assumed otherwise:

- **Right-to-left manga reading.** Left tap zone (40%) = *next* page, right zone = *previous*, center 20% toggles the toolbar. `←` is next, `→` is previous. The page slider is RTL, so its right end is page 1.
- Pages are a horizontally absolute-positioned strip moved with `translateX`. `<img>` elements are created lazily and evicted: `PREFETCH_AHEAD=8`, `PREFETCH_BEHIND=3`, `EVICT_AHEAD=14`, `EVICT_BEHIND=6`. Tests assert exact DOM cell counts derived from these — changing a constant means updating `test_strip_keeps_only_a_window_of_page_cells`.
- **The spread is the unit of both layout and navigation.** `rebuildSpreads()` groups pages into `spreads` (1 page in single mode, 1–2 in spread mode) and `idxToSpread`; every other function reads those instead of redoing the pairing arithmetic. A solo cover (`spreadOffset=1`), an odd trailing page, and a chapter spacer are all just 1-page spreads, so none of them need special-casing. Landscape defaults to a 2-page spread; `spreadOffset` (the `◀` button) toggles cover-solo pairing.
- **Chapters are sibling leaf folders concatenated into one `images` array.** `__spacer__` entries are inserted at a boundary so a chapter always opens on the right-hand page; `realToGlobalIdx`/`globalToRealIdx` map around them and the counter/slider work in *real* indices. Pairing runs over **global** indices (that is what makes the spacers do their job), then spacers are dropped from `spreads` — which is precisely what turns the page they padded into a solo spread. `gapBefore()` uses `CHAPTER_GAP_PX` (20) as the floor instead of `GAP_OUTER` at a chapter seam — same `Math.max(...)` widening rule as any other spread pair applies on top of it (監査 V3), so a chapter-start spread never lets the previous chapter peek in either.
- **Sizing is contain-fit computed in JS, not CSS.** `spreadMetrics(s)` fits a spread to the viewport from its pages' real aspect ratios (grow to `viewH`, shrink if that overflows `viewW`), then writes explicit px width/height onto the `.spread-container` and each `.page-cell`. That is why there is no slack around an image. Do **not** reach for `object-fit: cover` to fill the viewport — it fills by cropping, which is exactly what issue #13 forbids. `GAP_INNER=5` is the flex gap inside a spread; `GAP_OUTER=10` is **not** a floor — it lives purely in the position math (not a viewport margin, so a spread may span the full `viewW`) and is a *ceiling* candidate at best. Define `L(x) = (viewW - spreadMetrics(x).width) / 2` (the half-margin a spread `x` would sit in if centred alone). `gapBefore(s)` computes a `base` first — `CHAPTER_GAP_PX` (20) at a chapter seam (`spreads[s].chapterStart`), else `L(anchorSpread) <= 0 ? GAP_OUTER : Math.min(GAP_OUTER, L(anchorSpread) / 2)` (i.e. `GAP_OUTER` capped at half the anchor spread's own leftover) — then widens it: `gap = Math.max(base, L(s-1), L(s))`, for **every** spread pair, not just solo/odd ones or chapter seams, so a spread never lets the one beyond it peek into view: an ordinary 2P spread that doesn't fill `viewW` gets the same treatment as a solo cover, a solo trailing page, or a chapter-start spread, just at a smaller magnitude. `CHAPTER_GAP_PX` *is* a floor at a seam (nothing caps it the way `GAP_OUTER` is capped), while `GAP_OUTER` everywhere else is only ever a ceiling on `base` that the `Math.max` widening can still exceed. The accepted trade-off (監査 V3): at 900x600 a solo cover or a chapter-start page previously showed ~230–240px of the neighbouring spread; the iPad Air tight fit showed ~4.35px (now an ~8.7px black margin) — consistent with "a neighbour is never visible when a spread is centred." Aspect ratios are cached in `pageAR` and deliberately survive eviction; `<img>` elements are recycled through `imagePool`. Anything that changes the viewport, page mode, or `spreadOffset` must go through `invalidateSpreadSizes()`.
- **Positions are anchored, not absolute.** `spreadLeft(s)` measures from `anchorSpread` (the spread being read). A late-loading neighbour therefore cannot shift the current page — a real hazard once spreads have differing widths. Don't "simplify" this back to cumulative offsets from index 0.
- **Order matters when turning a page: animate first, re-base after.** `snapTo()` animates the track in the *current* anchor frame and only calls `rebaseAnchor()` on `transitionend`. Re-basing first cancels the slide — the containers' `left` jumps by exactly the distance the transform would have travelled, so there is nothing left to animate and the page turn becomes an instant cut. Re-basing is visually identity (every `left` and the transform shift by the same constant in opposite directions).
- **Rapid turns cut instead of sliding (burst mode).** `snapTo` demotes an animated turn to the instant path when a slide is in flight *or* the previous animated turn was under `SLIDE_MS` (300ms) ago, tracked by `lastTurnAt`; instant snaps (initial open, restores, orientation, reclaim) never open that window. Before this, every tap restarted the .3s transition from mid-flight — measured at 70ms taps the strip sat a constant 0.8 page behind `currentIdx`, one `transitionend` fired per 15-tap burst, and it kept sliding ~250ms after the last tap. The instant path also clears `sliding` itself because the superseded `settle()` is gen-guarded and never will. `tests/test_page_turn_burst.py` pins both the cut and the untouched single-tap slide.
- **Acknowledge first, load later.** A zone tap is acted on at `touchend` (`zoneActionAt(clientX)`, shared with the click handlers), not on the synthesized `click` that WebKit delivers ~40ms later; `touchend` calls `preventDefault()` so the synthesized click never happens at all, with `suppressClickFor` kept as a monotonic-deadline backstop (`suppressClickUntil`). Inside `snapTo` the synchronous path is only counter/slider, the target page's own cell (`ensureStripImage(idx)` + its `src`), `updateStripPositions`, and the rAF move; `ensureWindow`/`scheduleDeferredFetches`/`evictStrip` run two frames later under `windowWorkGen` (a newer turn cancels the older job). `.page-cell` has a dark background and a 1px inset border so the frame is visible before its image lands. Measured in the iOS Simulator (real Safari): tap→`snapTo` 40ms → 5–11ms, tap→first frame 60–97ms → 46–47ms, identical for next and previous. Tests that count strip cells or read every `src` right after a turn must wait for the window job (`window.__windowWorkDone` in test mode, or `wait_for_function` on the expected cell). `tests/test_tap_ack.py`.
- **Staged prefetch.** `ensureStripImage` sets `src` immediately only for the current page and its two neighbours; the rest of the `PREFETCH_AHEAD` window is parked in `data-deferred-src` and started by `scheduleDeferredFetches(idx)` once the next page (`idx+1`) has loaded, or after `DEFERRED_FLUSH_MS` (400ms), nearest-first, with `fetchPriority` high/low by distance. Cell counts are unchanged (only `src` timing), so `test_strip_keeps_only_a_window_of_page_cells` still holds; tests that read every strip `src` must first wait for all `src` attributes (`test_pages_are_natural_sorted`). Reason: a forward tap on a slow link used to land on a page still sharing bandwidth equally with seven far-ahead fetches while previous pages were already cached — the only forward/back asymmetry found. `tests/test_prefetch_staging.py`.
- **`?perf=1` page-turn profiler.** An on-device overlay (`#perf-overlay`) prints per turn: direction, tap→first-frame ms, tap→`snapTo` ms, sync work split (window/layout), and whether the target image was decoded at tap time. It exists because desktop Chromium, Playwright WebKit and the iOS Simulator all show forward and back turns within noise of each other (Simulator: ~40ms touchend→click, ~0ms sync, 60–97ms to first frame either way), so a reported asymmetry can only be measured on the real device.
- **Transition-event listeners on `#img-track` must filter.** Page images fade in with an `opacity` transition and those `transitionend` events *bubble* to the track. Every waiter (`snapTo`'s settle, both touch `finalize`s) goes through `isTrackSlideEnd()`; without it an image fading in mid-slide ends the slide early and snaps the strip. Also note `applyTrackTransform` forces a reflow before an animated move, because a settled slide leaves `transition: none` inline and setting both in one tick starts no transition at all.
- **URL state lives in the hash, `#/view/<folder>?p=<page>` for the viewer and `#/browse/<path>` for the browse hierarchy (browse = the folder level being browsed; root browse = no hash).** `folder` is the currently displayed chapter's path and `page` is the chapter-local index — the same semantics as the ReadingProgress keys. Opening a folder writes the hash with `pushState`; every page turn rewrites it in place with `replaceState`, so Back returns to the previous book, then the top page — never page-by-page through a book. `currentViewerState()` builds the state from `getCurrentChapterInfo()`, so in cross-chapter mode the URL names the chapter being read, not the top-level folder. Browse navigation pushes one history entry per level and the breadcrumb ↩ pops to the ancestor via a tracked URL stack — history never grows with duplicates; Back walks books, then folders, then top.
- **Browse-list scroll position is decided, not carried over.** `app/static/browse/scroll.js` (`window.BrowseScroll`) owns the decision: viewer-return (the chapter the reader was on), else a saved position, else the last read direct child in list order, else the top (the root works list always uses the top). The decision is kept as a **level-scoped intent** (`{level, anchor, via}`) re-applied idempotently while the level is unchanged — `restoreBrowse` runs twice per ☰ return, and a tile tap can be followed by `pushBrowseUrl`'s `history.go(-1)` pop, so a stale saved position must never overwrite a fresh decision. The intent expires on a different level, a `cause:'open'` replacement, `loadImages`, or `resetToTop`. `renderBrowse({scrollAnchor})` applies it in the same task as the `innerHTML` swap; `undefined` means "do not touch" (re-renders must never move the list). `#sidebar-scroll` is the real scroller (`#tile-grid` never scrolls).
- **History re-sync listens to `hashchange` ONLY** — never also `popstate`, which would run `applyUrlState` twice per traversal (the second invocation fires while the first load still has `images = []`, so it starts a redundant duplicate load and can duplicate history entries). Our own pushState/replaceState fire neither event, so a single listener cannot self-loop; manual address-bar edits re-sync through the same path — except an edit that changes only `s`/`o` (same folder+page) is not read back anywhere (layout prefs are runtime-only, see below), so it is silently overwritten by `replaceViewerState()`/`scheduleUrlSync()` on the next page turn.
- **Restores are token-guarded.** `applyUrlState()` waits for the folder tree (`treeLoaded`), then sets `urlRestoring` and calls `loadImages`, which claims `++urlRestoreGen` at entry. Every post-await continuation checks `myGen === urlRestoreGen` before writing anything, so a superseded load (e.g. a slow deep-link restore overtaken by a tile click) writes nothing. A restore replaces the current history entry instead of pushing. A dead or empty folder clears the hash and resets inline to a navigable browse state (sidebar open, the "no images"/"failed to load" message showing); `resetToTop()` — top prompt, clean URL — runs only from `applyUrlState()` when the hash is removed while a book occupies the viewer.
- **Deep links survive the OAuth round-trip** via the sessionStorage bridge key `bookq_return_hash` — a JSON `{hash, ts}` stashed by the login branch and restored by the init block only when `ts` is under 10 minutes old, then removed. A logged-out deep link therefore lands on the right page after sign-in.
- **Layout prefs live in the URL, not in localStorage** (decided 2026-09-21): viewer `#/view/<folder>?p=N[&s=1][&o=1]` — `s=1` = single-page in landscape (default 2P is not written), `o=1` = cover-solo pairing shift (dropped when `s=1`); browse `#/browse/<path>[?v=list|card]` (`tile` is not written; root browse with a non-default view is `#/browse/?v=list`). Layout changes use `replaceState` (Back never steps through layout changes). `s`/`o` are **not carried to the next book** — `loadImages` resets them unless it is a URL restore of that same folder. Search text and scroll positions stay runtime-only. Existing `?p=N$` test regexes remain valid because defaults are omitted. A browse URL without `v` (including the bare root reached via Back or the breadcrumb ↩) resets `viewMode` to `tile` and re-renders — the URL is the source of truth, so Back onto a pre-toggle history entry deliberately returns to tile. The breadcrumb ↩ history lookup (`pushBrowseUrl`) matches ancestor entries by browse path with the `?v=` query stripped, backward entries only, so a mode change never breaks the "Back walks books, then folders, then top" invariant; a dead folder clears its hash regardless of view mode.
- **A deep-link visit takes precedence over the stored reading position.** `loadImages`' saved slot prefers the URL page when its folder matches; the next page turn then overwrites the resume point via ReadingProgress — by design.
- **The resume point is mirrored server-side, one latest record per user.** `GET/PUT/DELETE /api/reading-position` (auth-required) reads/writes `app.state.reading_positions` — an in-memory dict keyed by user email, so a fresh browser or another device resumes via the same `続きから` pill. Container restarts lose it (accepted trade-off; the endpoint shape wouldn't change if persistence were added later). The server compares client `ts`: a strictly-older PUT returns `{"status":"stale"}` without overwriting, a `ts` more than `_POSITION_TS_FUTURE_SLACK_MS` (5 min) ahead of server time is a 400 (a wrong-clock write must not poison the slot — clamping is NOT a fix since a continuously-writing skewed device would stay ~slack ahead forever), and DELETE leaves a **tombstone** (wiped ts kept) so a stale in-flight PUT or another device's boot self-heal can't resurrect a wiped position (`?hard=1` clears it too — test mode only, for the conftest reset fixture). `app/static/progress/sync.js` (`window.ProgressSync`, a hard dep loaded before app.js — but `save()` still guards `window.ProgressSync` because a stale precached `/` can pair an old shell with a new app.js) owns the wire: `ReadingProgress.save` calls `push()` which is fire-and-forget — a 2 s trailing debounce, one in-flight PUT, keepalive — so rapid page turns cost microseconds on the turn path, never a request per turn. Failed sends requeue and retry on exponential backoff (4 s→8 s→…→60 s cap), and `push()` during backoff only swaps `_pending` (the armed retry timer stands) so reading through an outage can't shrink retries back to 2 s; 4xx except 408/429 drop the record. `visibilitychange`/`pagehide` save AND immediately `ProgressSync.flush()` in app.js's own handlers — ProgressSync's self-registered listeners fire earlier, so without that explicit flush the final save would die with the 2 s timer — but `_saveCurrentPosition` **skips the save entirely when the position is unchanged**: restamping localStorage's ts would let a later boot's self-heal assert a stale view over another device's newer record (the in-memory dedup key doesn't survive reload). Boot AND `visible`/`pageshow(persisted)` call `pull()` → `{ok, position}` through a single-flight guard (bfcache fires both events): a failed GET is never treated as "empty" — that would clobber a newer remote via blind self-heal. A strictly-newer remote lands via `mergeRemote` (no re-push, no echo), a newer local newest self-heals the server (ts merge, LWW — clock-skew between devices is a documented edge). Dedup is by position (`folder|page|total`), not ts — an unchanged save never overwrites another device's newer record; a same-position re-assert needs a real page turn (deliberate safe-side trade). `wipeClientData`'s 全消去 also DELETEs and `remove()` clears all local send state + aborts the in-flight PUT. The per-book progress map (50 entries, tile bars) stays device-local — only the single latest syncs. `tests/test_reading_position.py`, and `tests/conftest.py` resets the shared server's record (`?hard=1` DELETE + polls until the slot reads empty for a sustained ~300 ms — a previous test's keepalive PUT can land after a single check) before every `server`-using test.
- **Zoom and overview live outside the strip** (`viewer/gesture.js`, `viewer/zoom.js`, `viewer/overview.js`; spec `docs/superpowers/specs/2026-09-21-viewer-zoom-overview-design.md`). `#zoom-layer` wraps `#img-track` and is the only element zoom.js transforms; the strip's own `translateX`/transition are untouched, so anchor math is unaffected. The local `snapTo` calls `Zoom.reset(true)` first — every page turn (tap, swipe, key, slider, overview tap) lands at 1.0 — and its deferred window job (the same double-rAF that runs `ensureWindow`/`evictStrip`) ends with `Overview.markCurrent(idx)` so the prebuilt grid's `.cur` follows page turns; it is deferred because `scrollCurToThird` forces layout of the whole grid, which must not land on the acknowledging frame. The prebuilt grid parks every thumbnail URL in `data-src` (lazy loading keys on scrollport intersection, not visibility, so a live `src` would fetch on every book open); `show()`/`slideWindow()` hydrate it. `prebuild()`'s idle callback is a no-op when the grid is already built for `currentIdx`. `_teardownViewer` (hash.js) closes the overview and resets zoom because `resetToTop`/`restoreBrowse` never pass through `loadImages`; `loadImages` itself closes the overview at its head and prebuilds the grid after a successful load. **`window.snapTo`/`goNext`/`goPrev` are dormant twins in spread.js** — the live app.js locals are published as `window.viewerSnapTo`/`viewerGoNext`/`viewerGoPrev`; new modules must call those. While zoomed, `#zone-prev/next` are `pointer-events:none` and the center zone (20% everywhere now, zoomed or not — the zoomed-only widening rule was dead CSS and has been removed) means "back to 1.0"; an edge-turn fires only for a 1-finger drag that *started* with no horizontal room (clamped edge, or axis centred because `spread.width × zoom ≤ viewW`) and moved 80px with `|dx|>|dy|` (finger right = next, left = previous), rubber-banded and vibrated once at 80px. Pinch bands are absolute (`target = startZoom × ratio`, ratio measured from touch-down): `>1` zoom with midpoint anchor in container-local coords, `0.5<t<1` shrink toward the `.cur` cell, `≤0.5` fires the overview once (re-arms above 0.7). The 1-finger swipe tracks its `Touch.identifier` and counts fingers via `ViewerGesture.activeTouches(e)` (touches starting within 20px of a screen edge are palms until they move 10px; a *lone* palm that then moves is the swipe finger — app.js arms the drag late from `ViewerGesture.startOf(id)`, zoom.js seeds the pan the same way — so a thumb starting from the right bezel still turns the page). `ViewerGesture.findTouch`/`reducedMotion` are the shared helpers for the viewer modules. An edge turn at the first/last spread has nothing to turn to (`goNext`/`goPrev` return without `snapTo`), so `panEnd` settles the rubber band itself when zoom is still `> 1` after the call. Native pinch/tab-overview is suppressed by raw-count guards gated on `#viewer.contains(target) && images.length`, **all registered on `document` in the capture phase** — overview.js calls `stopPropagation()` on every touch event at `#overview`, so a bubble-phase guard on `#viewer` never saw a pinch inside the grid and Safari zoomed the page natively (pinch-in opened the tab switcher; a natively zoomed page then pans on horizontal swipe, which reads as "the left column is cut off") — the viewport meta was deliberately left without `user-scalable=no` (Simulator iOS 27: the guards alone stop Safari's tab-overview gesture). overview.js loads before app.js so its Escape/G listener wins via `stopImmediatePropagation`. `updateOrientation` early-returns when `innerWidth/Height` are unchanged, with a `-1` sentinel so the init call still runs. Overview/zoom state is never in the URL. Test helpers: `tests/viewer_touch.py` (CDP `Input.dispatchTouchEvent`; `touch_end(points)` lists the touches being **released**).

## Testing approach

`tests/conftest.py` synthesizes a downloads tree in a tmpdir (natural-sort cases, a 30-page folder, a single-child chain, a mixed folder, an empty folder, a Unicode-with-spaces folder), boots the real app on a random port in test mode, and drives headless Chromium. Fixtures `page` (390×844 portrait) and `landscape_page` (900×600) select the viewer mode. Touch-swipe gestures are deliberately untested — synthetic touch velocity is too flaky.

Server-side behavior currently has no unit tests; everything is asserted through the browser.

Performance budgets live in `tests/test_perf_budget.py` (deterministic: request counts, gzip ratio, long tasks — run with the rest of `tests/`). Millisecond KPIs are measured manually against the real-library dev host with `scripts/perf/measure.py`; targets and procedure are in `docs/performance.md`. `/api`, `/static`, `/sw.js` are gzipped by `app/compression.py`; `/image` and `/thumb` are never compressed or resized.
